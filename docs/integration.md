# Razorpay integration and operations

Phase 5 implements a secure webhook receiver and settlement-reconciliation API client.
The evidence is contract-tested offline using official-shape payloads. No live API call
or real-money transaction is part of the checked-in report.

## Official behavior implemented

- Razorpay signs the webhook request body with HMAC-SHA256 using the webhook secret.
- Signature verification uses the exact raw request body before parsing or casting.
- `X-Razorpay-Event-Id` identifies duplicate deliveries.
- Webhook delivery order is not guaranteed.
- A receiver should return a 2xx response within five seconds; failures can be retried
  with exponential backoff for 24 hours.
- When rotating a webhook secret, older retries may still require the previous secret.
- Test events are generated by transactions made in Razorpay Test Mode.

## Runtime configuration

Copy `.env.example` values into your secret manager or local environment. Do not
commit actual values.

```text
RAZORPAY_WEBHOOK_SECRET=<current webhook secret>
RAZORPAY_WEBHOOK_PREVIOUS_SECRET=<previous secret during rotation, optional>
RECONX_WEBHOOK_DB=data/runtime/webhooks.sqlite3
RAZORPAY_KEY_ID=<test API key id, only for recon fetch>
RAZORPAY_KEY_SECRET=<test API key secret, only for recon fetch>
ENABLE_RAZORPAY_IMPORT=false
ENABLE_LLM=false
OPENAI_API_KEY=<optional; only for on-demand advisory analysis>
OPENAI_MODEL=gpt-5.4-mini
RECONX_REVIEW_DB=data/runtime/reviews.sqlite3
```

The webhook secret is independent of the API key secret. ReconX requires a webhook
secret even if the Razorpay dashboard permits configuring a webhook without one.
Without `RAZORPAY_WEBHOOK_SECRET`, the receiver returns 503 and performs no processing.
The included Docker Compose configuration persists the SQLite delivery and audit ledger
in the named `reconx-runtime` volume across container restarts.

Configure the public HTTPS callback as:

```text
POST https://<host>/api/webhooks/razorpay
```

Subscribe only to the events currently supported:

- `payment.captured`
- `refund.processed`
- `settlement.processed`

Valid signed but unsupported events receive a successful `unsupported` receipt so they
do not create a retry storm; they are retained in the event/audit ledger without an
entity projection.

## Delivery outcomes

| Outcome | HTTP behavior | State effect |
|---|---|---|
| `applied` | 200 | Newest entity snapshot stored |
| `duplicate` | 200 | Delivery count and audit append only |
| `stale_ignored` | 200 | Event retained; snapshot unchanged |
| `unsupported` | 200 | Event retained; no finance projection |
| Bad signature | 401 | No database write |
| Event-id payload conflict | 409 | Transaction rolled back |
| Invalid/oversized/future payload | 422 | No database write |
| Receiver not configured | 503 | No processing |

## Settlement reconciliation client

The client calls only:

```text
GET https://api.razorpay.com/v1/settlements/recon/combined?year=...&month=...&day=...
```

It uses Basic API authentication, caps timeout at five seconds and limits the response
to 1 MiB. Payment net-credit, refund debit, adjustment amount and inclusive-fee/tax
relationships are checked. Invalid or unsupported items are marked unsafe for
reconciliation; they are never forced into canonical finance truth.

The guarded runtime endpoint is `POST /api/import/razorpay/{YYYY-MM-DD}`. Set
`ENABLE_RAZORPAY_IMPORT=true` only in an environment that contains Test Mode API
credentials. This endpoint deliberately returns unresolved groups until independent
bank and ledger evidence is supplied.

For a complete offline or exported-data loop, `POST /api/import/reconcile` accepts an
official-shape recon object and bank/ledger CSV text. The UI provides three file inputs,
runs the same policy, and downloads the resulting close pack. Input evidence is not sent
to the advisory model. A fully synthetic demo triplet is included under
`fixtures/razorpay/`: `settlement-recon-close-demo.json`, `bank-evidence.csv` and
`ledger-evidence.csv`.
